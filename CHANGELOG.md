# Changelog

All notable changes to Charter are recorded here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

Charter has no released versions yet. Development is in **Phase 1 — refinement only, no agent execution**: request intake, the refinement conversation, the spec confirmation card, and the approval queue. Agent execution, pull request creation, preview binding, teaching, and budgets arrive in later phases. The full build order is section 23 of [`agent-docs/spec.md`](agent-docs/spec.md).

Expect breaking changes without deprecation cycles until 1.0.

### Added

- Repository groundwork: license, contributor license agreement, trademark policy, security policy, contribution guide, and code of conduct.
- Identity behind a single provider seam: email and password (always available), plus GitHub, Google, Discord, and Slack OAuth when configured. Password verifiers use ASP.NET Core's `PasswordHasher`; the plaintext is never stored or logged. A federated sign-in links to an existing account and never creates one.
- Authorization: repository scope with deny by default, additive roles, transcript and code visibility gated on repository read access, and auto-dispatch policy resolution where a repository may only tighten organisation policy.
- First-run setup mode: an instance with zero users serves only the setup route and prints a one-time setup token to stdout. The token creates exactly one admin account, then setup ends permanently.
- Audit log write path, with authorization grants carrying the verb they should be recorded under.
- Refinement conversations are persisted, so a conversation survives the container restarting under it. Requester turns keep their type through storage: a reloaded turn refuses to be read as model-authored text.
- Model credentials: a `cursor_api_key` kind for the `cursor-agent` adapter, a separately tracked overflow allowance so the resolution chain's second tier can fire, a recorded reason when a credential is marked invalid, and a `429` with no reset header now records no reset time rather than a far-future placeholder.
- A refinement conversation read back out of Postgres becomes the live aggregate again, rules and all: the promotion gate, the unread-flag gate, and the confirmation. A confirmation is honoured only while the stored fingerprint still matches the stored spec, so a spec edited behind one comes back unconfirmed rather than dispatchable.
- The refinement thread is rebuilt from the stored turns. A clarifying question, an answer to it, or a turn submitted through `POST /api/requests/{id}/refinement` now survives a refetch instead of existing only in the live broadcast.
- User preferences are columns: theme, pane, and the requester onboarding timestamp join teaching level, so `PATCH /api/me/preferences` writes something instead of accepting the change and dropping it. An unchosen pane is stored as unchosen, which is what lets §12's role default — requesters to pane 1, engineers to pane 3 — apply until somebody picks.
- Requester feedback is recorded. `POST /api/requests/{id}/feedback` writes a row per verdict rather than only enqueueing a job, and the status thread renders the latest one back. Two buttons, *Works* and *Not quite*, as §11 specifies — there is no third.
- `pull_requests` records the head branch, so the engineer `Details` disclosure on the verification artifact card names it instead of showing a blank.
- **`IVersionControlProvider`** (change spec 001 part A.2): every version-control operation — authenticating a repository to a scoped short-TTL credential, describing a checkout, creating a branch, publishing a ref, opening a change request, commenting on one, labelling one, reading its state, comparing revisions, registering a webhook, and the optional create, transfer and protect operations — now sits behind one seam, with a capability model that says what a provider can actually do. GitHub is the only implementation, and it wraps the existing client rather than replacing it. There is still no way to express a merge, at either layer.
- **Change requests are opened from completed sessions.** When a session's runner reports a clean completion, the reconciliation pass publishes the session branch and opens a change request against the repository's base branch, recording its number, URL, head revision, branch and state. It is driven from reconciliation rather than from the result callback, so a control plane that restarted between the two still opens it, and a second pass is a no-op rather than a second change request. A session that produced no changes is recorded as exactly that — a real outcome with its own event and its own sentence, not an error.
- **Change request labels** follow the spec that asks for them: `unreviewed-spec` when the session was auto-dispatched (§7.5) and `schema-change` when the session's migration classification says so (§15). Where a provider has no labels, both facts are stated in the change request body instead of being dropped.
- **Change request state tracking** from the existing GitHub webhook, and §17 staleness: an open change request is marked stale when it is behind the base branch **and** overlaps it on changed files. Being merely behind is not stale — most open change requests are behind most of the time, and a flag that fires on all of them is one everybody ignores.
- **Onboarding verifies the merge gate** (change spec 001 part A.5). A repository whose base branch has no protection rule requiring review is reported as `advisory` rather than `provider_enforced`, warned about in the onboarding wizard, and recorded in the audit log whichever way the check comes out. Protection Charter cannot read is reported as "not verified", never as protected. `docs/security.md` gains a section stating this plainly.
- **A session that changed nothing has its own outcome.** §6 gains `NoChangesNeeded`, terminal and separate from `Failed`, because the agent running correctly and finding nothing to do is not a failure. The requester reads *"Nothing needed changing"*, with the sentence that matters underneath it: *"Nothing needed changing here. Most often that means what you asked for already works the way you wanted. Nothing went wrong, and there is nothing for you to do."* It notifies nobody and pages no engineer. Previously such a session ended as `Failed`, whose copy — *this turned out to be bigger than expected* — was the opposite of what had happened.
- **Preview environments can be reported by change request comment.** §18's fallback path is now connected end to end: the GitHub webhook delivery carries the comment's issue number, author and body, and an `issue_comment` listener hands them to the deployment ingestor. The parser and the binding already existed; nothing could reach them. The body is truncated on the way in and read only for a URL and a state, and a comment on a change request Charter did not open is ignored.
- **Change requests record their author.** `change_requests.author_login` is populated when the change request is opened, so §18's warning about Railway refusing to deploy a branch from an account outside the workspace can name the account to invite instead of saying "the author". A preview that never arrives with no explanation is the worst version of that failure.
- **Email delivery** (change spec 001 part C), behind an `IEmailProvider` seam with one implementation: SMTP. One implementation reaches SES, Postmark, Mailgun, Resend's SMTP endpoint, Google Workspace and a self-hosted relay, and needs no vendor account to test against. It is a hand-written client over `TcpClient`/`SslStream` rather than `System.Net.Mail.SmtpClient`, which cannot do implicit TLS. `CHARTER_EMAIL_PROVIDER=resend` is recognised and rejected with a message saying what to do instead, rather than treated as an unknown value.
- **`none` is a supported email configuration, not a broken one.** With no mail server, an administrator creating an account is shown the one-time setup link to pass on themselves; a failed send falls back to the same link, because the alternative is an account nobody can sign in to. Password reset by email is disabled with an explanation, and the link is never shown to whoever typed an address into the forgot-password form — anybody can type anybody's address into it. Every email-dependent setting reports why it is off and names the variables to set.
- **A test email can be sent from settings.** Through the real send path, not around it. Email misconfiguration is otherwise discovered when an invitation silently fails and a new hire cannot log in.
- **Notifications** (§22): one outbound abstraction, a per-user channel preference, and email as the only channel with an implementation. The notify-worthy set is a closed, tested list of exactly two states — `NeedsInput` and `PreviewReady` — checked once in the dispatcher rather than at each call site. §6 is explicit that notifying on all of them gets Charter muted within a week, and every other state is individually persuasive to whoever is adding it.
- **Templates in HTML and plain text** for invitation, password reset, *question for you*, *ready to try*, and the settings test. Both renderings are built from one structure, so they cannot drift. The copy follows §11 — plain language, no ETA, no jargon — and the requester-facing models have no field for a repository, branch, commit or cost, with a scrubber removing commit hashes, forge URLs and stack frames from the free text they do carry. A requester's own words are left alone.
- **Delivery failures are logged, recorded and returned** rather than swallowed, including a provider that throws: a notification is a side effect of a state transition, and a transition must not roll back because a mail server was down. The recent-delivery list is what the admin settings page reads; it is a table, retained for 30 days or 2,000 attempts.
- **The stores that were in memory are in Postgres** (§2.3): the per-user concept ledger, the walkthrough cache, the *explain this* daily cap, the per-user notification channel preference, and the email delivery log. Each replaces a working in-process default that lost everything on restart — a requester re-taught what a migration is because the container moved, a walkthrough re-billed to the teaching budget line for text that had already been written, and a delivery list that went blank on exactly the redeploy an operator reached for when mail looked broken. Four tables join `InitialCreate`: `notification_channels`, `email_deliveries`, `invitations` and `explain_this_usage`, and `concept_ledger` gains `last_referenced_at` (amending spec §5). No backfill: a user with no `notification_channels` row keeps the default of email on, Slack and Discord off.
- **Invitations are a row** (§30.2): email, roles, inviter, expiry, single-use redemption, and a SHA-256 digest of the emailed token. The token itself is never stored, so a database dump cannot be replayed against the redemption endpoint and a lost invitation is reissued rather than recovered. Redemption is one conditional `UPDATE`, so two clicks on the same link at the same instant produce one account and one refusal.
- **The email delivery log is retained rather than unbounded**: 30 days or 2,000 attempts, whichever comes first, pruned by Charter and not by an operator remembering to. A permanent record of every address this instance has ever written to is its own problem.
- **Outbound mail is rate-limited per recipient** in a sliding one-hour window, `CHARTER_EMAIL_MAX_PER_HOUR`, default 20. Account mail and notifications are counted in separate buckets so a burst of status mail cannot starve the invitation somebody is waiting for.
- Verification artifacts carry a jsonb payload for §27.7's kind-specific bodies: checksums and sizes for a build, the capture list for screenshots, counts and assertion text for a test report, device identifier and traces for a hardware-in-the-loop run. Nothing is invented at read time — an unrecorded field stays empty, an unprobed preview reports `unknown`, and a hardware run with no recorded outcome does not claim it passed.
- **Budgets are enforced** (§34, closing the hole §7.5 left where *budget caps* is listed among the things auto-dispatch never bypasses). `Budget` and `LedgerEntry` were rows nothing read; there is now an estimator, an evaluator and a reservation sweeper behind `AddCharterBudgets()`. Spend is **reserved before dispatch and settled after**, inside a transaction holding `FOR UPDATE` locks on the organisation's budgets — without that, ten concurrent sessions each pass the check and collectively blow the cap (§34.4). Nesting is conjunctive (§34.3): a session needs headroom in *every* applicable budget, and `reserved_amount` is a guaranteed floor that spends through an exhausted pool above it. Both currencies are governed separately (§34.1, §20b.5) — a subscription session costs no dollars, consumes a session of quota, and carries an imputed dollar figure so dashboards do not report it as `$0.00`. All five behaviours at the limit are implemented, and **every limit message names who can raise it**, by name and email where one can be resolved and by role otherwise (§34.5).
- Reservations expire on a two-hour TTL, so a control plane that dies mid-session does not strand budget. Expired holds stop counting against headroom immediately; a hosted sweep then releases the rows.
- `ledger_entries` gains `estimated_usd` and `estimated_quota_sessions`, kept after settlement overwrites the actual over them, so §34.4's *store actual-versus-estimate* is a measurable property rather than an aspiration. With three or more settled sessions for a repository and category the estimator uses the median of what they really cost; below that it prices token counts derived from the spec's scope. An unpriced model estimates zero and is labelled unpriced — sessions on one pass every dollar budget, which `docs/budgets.md` states plainly.
- **The engineer recap persists its structure, not only its prose** (§14). `recaps.payload` is a jsonb document carrying the summary, the deviations, what could not be verified, and the specification in full for an auto-dispatched session, built from the same scrubbed values as the markdown in one pass. `body_md` is unchanged and is still what gets posted as a change request comment. The verdict guard applies to both, so serving the payload cannot hand a reader a sentence §14 already removed from the body.
- Risk items carry per-file line counts and change kind. `RecapFileChange` has always had them and they stopped at the composer, so a reviewer's file list served `+0 −0` for every file. Counts are read from the transcript where the agent reported them, accumulated across repeated writes to one file, and never spread across several files named in one event. Zero still means *nobody counted* rather than *nothing changed*.

- **`NeedsInput` is entered, and it notifies** (§6, §22). It was the other half of the pair `PreviewReady` was in until recently: present in the enum, the label table and the projection, and set by nothing — so an agent that stopped to ask a question reached nobody and the session sat there. A `question` event on the runner callback now moves the session and the request to `NeedsInput` and tells the requester through the one notification seam, which keeps the §6 gate; the callback announces only a genuinely new event, so a redelivered question tells nobody twice. The question appears on the status thread as well as in the mail, because somebody who follows the link should not arrive at a card that says *Question for you* and does not say what it is. Answering it — in the same box the requester refined in, §11's one thread — puts the session back to `Running`, records the answer as an event, and queues the dispatch that resumes it.
- **Refinement streams while it happens** (§11). `RefineJobHandler` wrote correct rows and published nothing, so the first thing a requester ever experiences updated only on reload — the 5–20 minute silent gap §11 says reads as broken. Each turn now publishes the messages it appended, the proposed spec, the new status, and the typing indicator going off. The frames are rendered by the same projection `GET /api/requests/{id}` uses, so a live view and a refetch cannot disagree about a message id, a body or an acceptance criterion; `Charter.Orchestration` depends on a narrow seam expressed in rows rather than on `Charter.Api.Contracts`.

- **The runner publishes what the agent changed** (§2.2, §6, §7.3). After the agent CLI exits and the checks are classified, the session shim stages the work, checks **every staged path** against the path scope, commits, pushes the session branch, and emits `branch_pushed` carrying the branch and the resulting revision. That event is what `ChangeRequestPublisher` opens a change request from, and until now nothing in Charter wrote it: every clean session ended as `NoChangesNeeded`, no change request opened, no preview bound, and the requester saw nothing. The second scope check is the important one — it is enforced on what is about to be committed rather than on what the agent said it wrote, so a write the agent never announced fails the session and nothing at all is committed. A session that genuinely changed nothing emits `no_changes` and completes; a push that could not happen fails loudly. The two are never conflated, because a broken credential must not read to a requester as an agent that decided there was nothing to do.
- **Charter's commits are attributed to the person who asked.** The requester is both author and committer of the commit a session produces. There is no bot identity, no machine account, and no attribution trailer of any kind; the message is the specification's title and opening paragraph, and any byline-shaped line in the specification is stripped on the way in (§24). That Charter produced the change is stated on the change request, in words, which is where a reader can act on it.
- **Milestones are promoted as a session runs** (§11). Pane 1 was silent for the entire build — the longest silent window in the product, and precisely the 5–20 minute gap §11 says reads as broken. Events are now promoted into the four requester-facing milestones as they arrive: *understanding the current setup*, *making changes*, *checking it works*, *putting it together*. Promotion is forward-only and once each, so a redelivered stream is still one thread and a build never appears to start over. Each milestone points at the event that produced it, which is what makes §12's pane 1 to pane 2 linkage real. Nothing predicts a finish: elapsed only, never an ETA.
- **`CHARTER_RUNNER=docker` runs sessions.** The Compose self-host backend of §2.2 is implemented behind the existing `IAgentRunner` seam: it spawns a sibling container from the repository's runner image, running the same shim the shipped workflow runs, with the path scope in its environment and per-repository cache volumes (§32.3). Dispatch is idempotent against the daemon's own labels and cancellation finds the container by its session label, so neither depends on the control plane remembering anything across a restart (§2.3). The container has no repository secret to exchange the way the workflow does, so the three per-session credentials — a callback token, a single-repository version-control token, and a scoped model credential — are minted at dispatch and passed as container environment, never written into the queue row; and because it starts empty, the shim clones the repository at the base commit for itself when its workspace is not already a checkout. Two limitations are documented rather than papered over: capabilities are declared instead of probed, because the machine that will run the work does not exist until dispatch; and Charter will not talk to a Docker daemon over TCP. `CHARTER_DOCKER_SOCKET` overrides the socket path, and a `unix://` `DOCKER_HOST` is honoured. Previously this value parsed, validated, registered no runner, and queued every session forever with no error anywhere.

- **The session runs the repository's own checks** (§8). The named validation commands in `.charter/config.yml` run in the sandbox after the agent exits and before the branch is pushed, in declaration order, and each outcome reaches the transcript as a `check_result` event and the change request body as a line an engineer reads before the diff. A repository that declares none is told so in the body — "nothing was verified automatically" — because a blank space and a green run are not the same claim. **A failing check is reported and does not block the push**: Charter has no merge button, so a red change request cannot ship on its own, and discarding the work would burn everything the session cost while leaving the engineer nothing to read, nothing to take over, and no evidence about what went wrong. What *does* stop a session is a check whose toolchain the image lacks, and it stops it **before the agent starts** — a declared `dotnet build` on an image with no .NET SDK fails immediately with a message naming an image that has one, rather than installing a runtime (§32.1) or spending a model's time producing work that could never have been validated. Each check is one command with an argument vector and no shell; a `run:` containing `&&` or a pipe is reported as a check that could not be run rather than quietly passing. Checks are skipped entirely when the agent changed nothing. Previously nothing ran them, so Charter opened change requests without ever knowing whether the code compiled, and §14's recap had nothing to put under *what it could not verify*.
- **`InReview` and `Merged` are reachable** (§6). They were the last two states in the state machine and nothing set either from the provider, so a request stopped at *Ready to try* forever and the requester was never told the thing the whole pipeline exists to tell them. A review or a review request on the change request now moves the session and the requester's thread to *An engineer is checking it*, and a merge moves both to **This is live**. Charter still decides nothing about the code — reviewing and merging happen on the provider, outside the trust boundary (§7.4) — and neither state notifies, because §6 keeps the notifying set at exactly two. GitHub Apps must be subscribed to **Pull request review** as well as **Pull request**; `docs/self-hosting.md` says so and says what is lost without it.
- **Staleness is recorded where somebody will see it** (§17). A change request marked stale — behind the base branch **and** overlapping it on changed files, both halves still required — now appends a `change_request_stale` event to the session's transcript, naming the branch that moved and saying that a rebase is needed. The session is deliberately not retired for it: `Stale` is terminal, and §17's remedy for a stale change request is a rebase rather than an ending. Previously the flag was set on a row nothing read.
- **Demo mode** (§30.6). `CHARTER_DEMO=true` seeds a demonstration organisation, a repository that finished onboarding, two completed sessions with their transcripts, milestones, verification artifacts and engineer recaps, and one request still in refinement — then blocks every outbound call. The block is at the client factory rather than on a list of clients, so a model provider, the OpenRouter catalog, the GitHub App, an OAuth exchange, Railway and the preview probe are all refused before a socket opens, and so is an HTTP client nobody has written yet. SMTP is refused too and email degrades exactly as `CHARTER_EMAIL_PROVIDER=none` does. Postgres and an operator's own Seq or OTLP collector are deliberately untouched: the promise is that evaluating Charter costs no token and needs no GitHub App, not that the container may not reach the log server it was pointed at. Seeding is skipped on a database that already holds an organisation, so the variable is safe to leave set across restarts. Previously the variable parsed, validated, and had no consumer anywhere.

- **The daily release check exists** (§28). Charter reads the public GitHub Releases API once a day, compares the newest tag on the configured channel against the version compiled into the build, and records what it found. It runs as a `update_check` job on the Postgres queue rather than on a timer, so one replica performs it, a restart resumes from the row, and the schedule survives a container that dies mid-check. The cached result is the payload of the next scheduled check, which is why no table was added for it. `[SECURITY]` and `[MIGRATIONS]` markers in a release are carried through, so a security release and an upgrade that needs a backup are distinguishable from an ordinary one. Failures are silent by design: an offline, air-gapped or rate-limited instance keeps the previous answer, completes the job, and logs nothing above debug — a daily error is how operators learn to stop reading logs. `CHARTER_UPDATE_CHECK=false` does not disable a call at the call site; it means the component capable of making one is never constructed, and a handler is still registered so that a check queued while it was on is drained rather than deferred round the queue forever. `CHARTER_DEMO=true` suppresses it the same way. Previously both variables parsed, validated and reached nothing.

- **The onboarding wizard shows what recon found** (§9). `GET /api/repos/{id}` now carries `proposedScope`, `lastSmokeTest.checkpoints` and `primerDraftMd` — three fields the web app had typed and read from the start and no endpoint had ever sent. Recon's proposal is recorded when the run reports, so it outlives the request that produced it: §9 makes the proposal the thing an engineer *edits* before a repository is requestable, and a proposal that existed only inside the pull request left the scope-confirmation screen with an empty file tree. The deny-by-default floor comes back as locked rows with the reason attached rather than as toggles the server would filter out anyway. The smoke test reports all six integration points individually, with everything after the first failure `skipped` rather than `failed` — a preview that was never asked to deploy did not break — and the empty-preview caveat rides on a passing run as a warning, never as a block. The primer draft is scaffolded from the facts recon verified and left deliberately unfinished where the domain paragraphs go, because a draft that reads as finished gets published unedited.
- **Repository access has a screen** (§7.3, guardrail 1). `GET` and `POST /api/repos/{id}/access` existed and nothing called them, so an onboarded repository was requestable by nobody with no way to see or change who could ask it for anything. The onboarding page now lists the grants — by role and by person, each named rather than shown as an id — and says the default out loud instead of rendering an empty table, because deny by default means the absence of a row *is* the refusal. Withholding writes a refusal rather than deleting a grant, and the screen states that a repository whose smoke test has not passed is invisible whatever the grants say, since the two conditions are independent and an admin who has just granted access needs to know why nobody can see it yet.
- **Members, roles and the audit log** (§7.1). `member.role.granted` and `member.role.revoked` had been in the audit vocabulary from the beginning with nothing writing them: privilege escalation is the single thing an audit log must never miss. `GET /api/members` and `POST /api/members/{id}/roles` add or remove one role at a time — never a whole set, which would replace state the caller read minutes ago — and every change that changes something writes a row naming the administrator who made it, while a change that changes nothing writes none. Two refusals, both with a sentence rather than a bare 403: leaving somebody with no role at all, and removing the last administrator on the instance. `GET /api/audit` reads the log back for an admin, leading with a plain-English sentence and keeping the dotted verb beside it, and shows the entries nobody is named for rather than hiding them — §7.3 says the agent never acts on its own initiative, so those are the rows worth being able to find.

- **Model credentials can be linked, listed and revoked over HTTP** (§20b.2). `GET`, `POST` and `POST /{id}/revoke` under `/api/credentials`, engineer and administrator only, checked on the server rather than hidden in the client (§7.4). The absence of this was half of why the resolution chain never resolved anything: §20b.3's first four tiers read `credential_grants`, and nothing in the application could write a row to it — the only working procedure was to encrypt a key by hand and `INSERT` it, which nobody would ever discover from the documentation. The secret arrives once, is encrypted with `CHARTER_CREDENTIAL_KEY` before it reaches the database, and no response type has a property that could carry it back out; the list shows provider, owner, scope, status, invalid reason and last used, and there is no reveal. Instance-level keys appear in the same list marked `environment`, since an operator asking what this instance can authenticate with needs the variables in the answer. Each entry also carries whether the configured `CHARTER_MODEL_REFINE` and `CHARTER_MODEL_TEACH` can actually be served, with the remedy — answered by the real resolver, so the screen and the refine job cannot disagree. Linking and revoking are audited as `credential.linked` and `credential.revoked`. Opting a credential into a shared pool returns §20b.7's terms-of-service caution rather than doing it silently. **There is no web surface for this yet**: the routes exist and are tested, and the settings screen that would call them is not built.

### Changed

- **Object storage works, on three explicitly selected backends** (§2.3, §4.1, §4.2, §27.1). The `CHARTER_STORAGE_*` block used to parse, validate and reach nothing at all; it now selects `none` (the default — everything in Postgres, and the only correct answer on a platform whose filesystem is wiped on deploy), `filesystem` (a directory on a durable volume, for a self-hoster on a VPS), or `s3` (AWS, Cloudflare R2, MinIO, Backblaze B2, Wasabi). Spec §2.3's *no durable local disk* is amended to say what it always meant: it is a PaaS constraint, and an operator who has a real volume and says so is not covered by it. **The backend is named, never inferred from which variables happen to be set** — inference means a typo in a variable name silently changes what an instance does. A backend that cannot work stops the boot as a named `object storage` preflight line: a misspelled backend, a path that is missing or read-only, a bucket block that is incomplete, or a storage variable set while the backend is still `none`. Neither key is ever printed. **If your instance already had the bucket variables set, add `CHARTER_STORAGE_BACKEND=s3` before upgrading** — see [upgrading.md](docs/upgrading.md).
- **Oversized transcript output is offloaded to the store instead of into a Postgres row** (§5, §19). `events` is the largest table Charter has, and what makes one row large is a single string inside it — an agent's `Write` tool call carries the whole file it wrote, a failing check carries its build log. With a store configured, a string over 8 KiB moves into it and the event keeps the end of the text plus a `file_ref`, a byte count and a SHA-256. Nothing changes on the default backend: the payload is stored exactly as it arrives, as it always was. A store that is unreachable never fails a session — the event is written whole and the failure is logged.
- **Stored bytes are read back through Charter, never through a link** (§7.4, §16). `GET /api/requests/{id}/blobs/{key}` serves an object behind the same permission as the transcript pane. There are no public bucket URLs and no presigned links anywhere in the subsystem, and no setting to enable them, because a URL that authorises whoever holds it would turn an engineer-only artifact into a public one the moment it was pasted into a chat. Object keys built from untrusted components — a check name out of a repository's `.charter/config.yml`, a path out of an agent's tool call — are reduced to a single safe path segment, and every read is checked against the session the caller was authorised for. Objects are capped at 8 MiB each; Charter never deletes them on a schedule, so retention is a bucket lifecycle rule or a cron over the directory, documented as such in [privacy.md](docs/privacy.md).
- **`PullRequest` is renamed `ChangeRequest`** throughout the data model, the API and the code (change spec 001 part A.2, amending spec §5). The table is `change_requests`, `deployments.pull_request_id` is `change_requests.change_request_id`, and the API's engineer `details` payload renames `pullRequestNumber` and `pullRequestUrl` to `changeRequestNumber` and `changeRequestUrl`, alongside a new `changeRequestTerm` carrying the provider's own word — *pull request* on GitHub, *merge request* on GitLab — so the UI stops hard-coding one provider's vocabulary. This is a breaking API change; there are no released versions, and the initial migration was amended in place rather than a rename migration being added.
- **The control-plane model defaults are OpenRouter-qualified.** `CHARTER_MODEL_REFINE` and `CHARTER_MODEL_TEACH` now default to `openrouter/anthropic/claude-sonnet-5`, reached by `OpenAiCompatibleModelClient`: one implementation, one key, every model. The native Anthropic and Gemini clients stay registered and are used the moment an `anthropic/` or `google/` identifier is configured — this is a default, not a deletion. An instance holding only an `ANTHROPIC_API_KEY` should set those two variables explicitly or add an `OPENROUTER_API_KEY`. `CHARTER_MODEL_BUILD` deliberately does **not** change: it is handed to an agent CLI, not called by Charter, so it stays a bare Anthropic name the default adapter can actually run (spec §4.2, §20b).
- **`adapters/pi.yml` rewritten against pi's published CLI reference.** The shipped file was the illustrative snippet from spec §12b and was wrong in four ways: `--mode json` is the event stream (`--print` is a different mode and `--output-format` does not exist), the message is a positional argument, `--provider` and `--model` are separate options, and the JSONL events are `tool_execution_start` / `message_end`, not `tool_call` / `assistant`. Spec §12b's worked example has been corrected to match. `steering` is no longer claimed for `pi` or for `claude-code`: pi steers through `--mode rpc` and Claude Code through `--input-format stream-json`, neither of which the shim speaks yet.
- **Adapters declare the model identifier form their CLI expects**, through a new `model_format` key — `bare` (the default, and what Charter dispatched before), `qualified`, or `verbatim` — plus a `{provider}` placeholder for a CLI that selects the provider separately. `claude --model anthropic/claude-opus-5` and `opencode run --model claude-opus-5` are both unknown-model errors, and the caller no longer has to know which is which. Existing adapter files keep producing exactly the command they did before.

### Security

- **The deployment webhook was unauthenticated, and the URL it accepted was used two dangerous ways** (§16.3, §18.1, §27.7). `POST /api/deployments/{prSha}` was mapped with no authorization at all, and its only admission rule was the head commit SHA in its path — a value the execution plane authors, so a session holds it before the control plane does, and one that is then public on the change request page, in every fork, in CI logs and in notification emails. The URL in the body was checked for non-emptiness and stored raw. Charter then did two things with it. It fetched it on every reconcile tick from inside the control-plane container on a bare `HttpClient` whose only rule was the scheme, which is a recurring server-side request forgery against anything the container can reach, instance metadata at `169.254.169.254` included. And it rendered it as the requester's preview button, copy-link and QR code underneath Charter's own fixed sentence, *"Nothing you do here touches the real one"* — a promise made on Charter's authority to the person least equipped to evaluate a link. Admission is now `CHARTER_DEPLOYMENT_WEBHOOK_SECRET`, presented as `Authorization: Bearer`, as `X-Charter-Deployment-Secret`, or as `?token=` for a platform whose post-deploy hook is a URL field and nothing else; the SHA still decides which change request a report binds to, and an instance with no secret set refuses every report rather than falling back. **This is a breaking change for anyone whose platform posts to that endpoint** — see [upgrading.md](docs/upgrading.md). Every preview URL is now validated once, before it is stored, at the binder both ingestion paths share: `http(s)` only, no credentials in the userinfo, and no host that resolves to loopback, link-local, private, CGNAT or unique-local space, with resolution deciding because a name can point anywhere. A refused report is recorded as a failed deployment with no URL, so the card reaches §11's designed failure instead of spinning on a preview that is not coming. It is checked again before the publisher writes it onto an artifact and again in the API projection, because rows written before this existed are still in the database and an upgrade does not rewrite them; the probe's client resolves and checks the address at the socket, follows no redirects, bounds the response and sends no credentials; and the card refuses to render a link, a copy button or a QR code for a URL that fails, whatever the API sent. `CHARTER_PREVIEW_ALLOW_PRIVATE_HOSTS=true` re-admits private ranges for a self-hoster whose previews genuinely live on their own network, and re-admits neither loopback nor link-local.
- **The credential exchange authenticated a repository where it should have authorised a session** (§7.4, §16, §33.5). `POST /api/runners/sessions/{id}/credentials` is the route that mints a contribute-scoped GitHub token and a twelve-hour callback token, and the only thing it checked was `secrets.CHARTER_SESSION_SECRET` — one value per repository, read by every workflow run in it. Proving you are a run in a repository is not proving which session you are, so any run in repository R could name any *other* live session of R and be handed that session's repository token, its callback token, and with them the ability to write that session's transcript and report it failed. That included sessions running on a Charter Agent, which never uses this route at all. The event token was already session-bound; the exchange now reaches the same standard by requiring a second factor — a per-session token minted at dispatch and delivered only in that session's `client_payload`. Neither factor substitutes for the other: the repository secret never appears in a payload anybody with repository read access can see, and the session token grants nothing without it. **This is a breaking change to the shipped workflow file**; the repository secret and its derivation are unchanged, so nothing needs rotating, but every target repository needs the current `.github/workflows/agent-session.yml` and a stale one fails its first step with a message naming the file. See [upgrading.md](docs/upgrading.md).
- **The Charter Agent's mint had no liveness gate at all** (§6, §16, §33.5). The HTTP exchange refused a session that was terminal or undispatched; `AgentConnection.MintAsync` checked neither, and issued the same contribute-scoped GitHub token and twelve-hour callback token on any claim. Cancelling a claimed session fails its job, and a failed job with an attempt left returns to `Pending` — so pressing cancel could be followed by fresh credentials being handed to whichever agent claimed the row next, for work that had already been called off. Both paths now pass one shared gate: no credentials for a session that has ended, has a cancel in flight, or that no backend has dispatched. The gate also reads the repository from the session's own record rather than from the queue row's payload, so a token follows the session rather than whatever a row claims. A refused job is settled rather than handed back, because dead work re-offered on the next claim is a loop.
- **Cancel could reach the wrong copy of a job on a Charter Agent** (§33.4). A duplicate grant of a job already running on a host overwrote its entry in the daemon's running-job map, dropping the first job's cancellation source: the first shim kept running with nothing holding its token, so cancel, revocation and lease expiry all reached the second copy and none of them the first — and the first would go on to push a branch. The agent now keeps the copy it is running, extends its lease, and starts nothing new; the daemon refuses to overwrite a live handle whatever it is told.
- **Charter took the workflow run URL at the runner's word, and then acted on another repository with it** (§2.1, §11, §16). `run_url` is reported by the runner — on the credential exchange and again as the `session_started` event — and it is authored inside the sandbox, in the same process as an agent reading repository content nobody vetted, so it is reachable by prompt injection. Charter folded it into the session's external reference and then parsed the *repository* back out of it, so a run could name any repository it liked and have cancelling that session issue `POST /repos/{that-repo}/actions/runs/{id}/cancel` against it, with the instance's own credential, against **any other repository connected to the instance**. The quieter half is the one that costs money: the run that was supposed to stop was never touched, and §11's cancel path was told it had been, so the session settled as cancelled while an agent kept running and kept spending. The reference is now checked against the repository the session belongs to — read from the session's own record, never from anything a caller sent — at both places it is recorded, and the callback carrying a mismatch is **refused** rather than cleaned up: a reference naming another repository is a lie, not a formatting problem. A mismatch at the exchange mints nothing at all. The check runs again at cancellation, because rows written before this existed are still in the database and an upgrade does not rewrite them. Anything that is not an absolute `http(s)` run URL is refused too, which closes the same hole in the other two backends, where the reference is read as a container id and as an agent job id respectively. **A repository renamed on GitHub and not reconnected in Charter now fails its sessions at the first callback**, with a message naming the repository on record; see [runners.md](docs/runners.md).
- **A cancel that stopped nothing could report that it had** (§11). Beyond the run URL above: cancelling on Docker acted on the recorded container id without checking the container was this session's, and cancelling on a Charter Agent acted on a job id read out of the reference without checking the job's payload named this session — both then answered *stopped*. Neither acts on an unverified handle now: Docker kills only containers carrying the session's own label, the agent plane falls back to this session's own row, and every path that did not end in the run being confirmed dead returns "nothing was stopped" with a sentence saying where to look. The control plane logs that outcome at warning level rather than information, because a session that settles as cancelled while its runner is still spending is exactly the thing an operator needs to find.
- **A session could publish a branch it did not own, including `main`** (§7.4, §16.3). `branch_pushed` carries a branch name, the publisher believed it, and `GitHubVersionControlProvider.PushAsync` then issued `PATCH /repos/{owner}/{name}/git/refs/heads/{that branch}` with a contribute-scoped token. The push is fast-forward-only and that is no defence: an agent's commit is a descendant of the base branch in exactly the ordinary case, so one event reachable by prompt injection could advance the ref branch protection and CODEOWNERS exist to hold — with no merge, no review and no pull request — and nothing in the publish path consulted branch protection. Charter now publishes only `charter/session-<id>`, computed from the session's own id, and **refuses the publication whole** when a report names anything else: no ref moved, no branch created, no change request opened, the session ended as failed with the reason on its transcript, and a warning naming the reported branch in the operator's log. Substituting the right branch quietly would have published a revision that was never pushed to it and left nobody a reason to look. A runner that reports no branch at all is unaffected — the convention applies, as before. **If you wrote your own runner, it must push to `charter/session-<id>`**; see [runners.md](docs/runners.md).
- **A file path from a transcript could address a different repository on the API host** (§7.3, §16.3). The code pane's path normalisation swapped `\` for `/` and trimmed a leading `/`, and nothing removed a `..` segment. `Uri.EscapeDataString` leaves `..` intact because `.` is unreserved, and every GitHub URL is built with `new Uri(apiBase, path)`, which applies RFC 3986's dot-segment removal — so a path under `repos/{owner}/{name}/contents/` with enough `..` in it resolved somewhere else entirely, with the session's installation token attached. The allowlist was no defence, because it is built from the same `file_write` events through the same normalisation. Kestrel collapses `..` and `%2e%2e` in a request target before routing, but `%5C` decodes to a backslash and is not a separator, so `a%5C..%5C..%5C..` reached the endpoint intact and the translation turned it back into a climb. Paths that are not repository-relative — a dot segment, a leading `/`, a backslash, a percent sequence, an empty segment, a colon, a control character, or over 1024 characters — are now refused rather than rewritten, and the reader gets the same *no such file* the pane already gives for a file outside the change. The GitHub client refuses a dot segment in **any** path, ref or revision it puts in a URL, so the guarantee holds for a caller that forgets. Per-repository token scoping meant a cross-repository read would have been refused by GitHub; the request should never have left `repos/{owner}/{name}/` regardless.
- **Check output was spliced into the pull request body as live markdown** (§8, §14, §16.3). The body is a document Charter authors and an engineer reads as Charter's own account of the session, and the check names and summaries in it come from the sandbox. Unescaped, unbounded and with newlines intact, a summary could put a link somebody clicks or an `@mention` that pages a real person into Charter's voice, open a blockquote that fakes §7.5's *no human approved this specification* disclosure, or start a heading that hides the failing-check block underneath it — and an unbounded transcript could push the body past GitHub's size limit and fail the create call, so a session could stop its own work being reviewed by talking too much. Names and summaries are now rendered as inline code spans, which are inert by construction rather than by an escape table that has to be re-audited: flattened to one line, cut at 100 and 300 characters, at most twenty checks listed with the remainder counted. What a failing check said is no longer repeated in the roll call at the bottom of the body; the full output is on the transcript, as before.
- **A lease left out of a heartbeat acknowledgement did not stop anything** (§33.4). The wire contract says a job absent from an ack has lost its lease, and the control plane leaves one out precisely to say stop — to a sweep, a cancellation, or another worker taking the claim. The agent read only the renewals, so the work carried on until its own TTL happened to run down, a window in which another runner can hold the same session and both push the same branch. Omissions now stop the local work at once, matched to the heartbeat they answer so a job granted in the meantime is not caught by it, and nothing is reported for a job whose claim is already somebody else's.

### Fixed

- **The documented default installation could not make a single model call.** `ANTHROPIC_API_KEY` and `OPENROUTER_API_KEY` satisfied startup validation *and* the §30.1 model-credential preflight check, so the instance reported healthy — and then `EfModelCredentialStore` read `credential_grants` and nothing else, while no API anywhere created a grant. The instance-level key was validated at boot and never consulted at resolution time. The observed behaviour on a real boot: preflight passes, a request is filed, and it sits in *Let's figure out what you need* silently forever. Both variables are now tiers in the §20b.3 chain, at the tiers they already are — `ANTHROPIC_API_KEY` is an organisation metered API key (tier 4) and `OPENROUTER_API_KEY` is OpenRouter (tier 5) — projected as ordinary candidates of the matching kind, sorted last within their tier so a grant an operator linked for the organisation still wins. Nothing is written to the database for them: the environment is the source of truth, and a row would diverge the moment the variable changed. The whole suite passed while this was broken, because the one test that drove a request through a real Postgres stubbed the credential resolver.
- **A session that cannot resolve a credential now fails loudly instead of stalling.** Resolution reported "nothing resolved" and the refine and recap handlers deferred on all of it, so a missing, revoked or invalid credential queued the job again every ten seconds forever with nothing written anywhere. §20b.3's *it does not fail* applies to a rate limit with a reset instant, and to nothing else — an invalid key, a revoked grant, an empty chain and a `429` with no reset are all cases where waiting produces nothing. Resolution now says which of the three it is, and the refine handler ends the request in `Failed` (§6) with a sentence the requester can read — *"Charter could not reach a model to work on this... this instance needs a model credential set up"* — while the actionable half, naming the exact variable to set for the exact model that could not be served, goes to the log and to the job's recorded error where the operator is looking. No environment variable appears in front of a requester (§7.4), and no part of a key appears anywhere (§19).
- **The first-run model-credential check says when a key cannot serve the configured model.** "A key is set" and "a key can serve `CHARTER_MODEL_REFINE`" are different questions, and only the second decides whether a request refines: an `openrouter/`-qualified identifier — which is the §4.2 default — can be served only by an OpenRouter key, so an instance carrying nothing but `ANTHROPIC_API_KEY` passed the check and then resolved nothing on the first request. The passing line now names any control-plane model the instance keys cannot serve. It reports rather than blocks, because a linked grant this check cannot see may serve it.
- **`CHARTER_DEMO=true` produced an instance nobody could sign into.** Demo mode seeded an organisation, a repository and a week of completed sessions, and seeded no password identity for either of the two users it created — so the accounts existed, sign-in refused all of them, and seeding had already ended setup mode, so no setup token was printed either. The command documented as the way to look at Charter booted a fully populated instance and locked the evaluator out of it. Both accounts now carry a password identity, written through the same hasher sign-in verifies against and read back by the ordinary password provider: same PBKDF2 verification, same throttle, same session cookie, same role checks, no demo branch anywhere in authentication. The credentials are printed at startup in a block modelled on the setup token's, in the place the token would otherwise be, so nobody has to read source to get in. **The two accounts are the point**: `priya@northwind.example` holds `requester` and `ada@northwind.example` holds `admin`, `engineer` and `approver`, so signing in as each in turn shows §7.4's omission working live — the requester's request body has no `transcript`, `changes`, `recap` or `sessionActions` key, and the transcript, diff, members, audit and runner endpoints answer `403` to her. The password is documented, and therefore public; what keeps that safe is that the seeder refuses to write into a database that already holds an organisation **or a user**, so a well-known password can never appear on an instance holding real work, and the startup banner says in as many words that the instance should be treated as public and the database discarded before real use.
- **The demo instance was thin in the places an evaluator looks second.** The administrator held three roles and no repository grant, so `canFileRequests` was false, her project list was empty and the instance looked broken rather than locked down — deny by default applies to everyone, so the engineer role now carries an explicit grant of its own. Budgets and the cost ledger were empty next to sessions that plainly cost money, which reads as an accounting bug; an organisation cap and a per-requester cap are seeded, with each session's build and recap cost reserved and settled against them the way §34.4 requires. The audit log rendered only the evaluator's own sign-in, so the week's history — the instance being claimed, the repository connected, recon proposing a scope, the smoke test passing, the primer published, the requester invited and accepting, both grants, and the two spend approvals — is seeded as attributable rows, which is what §7.3's fifth guardrail exists to make visible.
- **A Charter Agent could claim the control plane's own work, and then fail it.** The queue's capability filter is a containment test — a runner claims a job when the job's requirements are a subset of what the runner advertises — and the empty set is a subset of everything. Refinement, the engineer recap, the daily release check, repository onboarding and the control plane's own build jobs are all queued requiring no capabilities, because they run in-process and need nothing from a runner. So any daemon that happened to be online could claim them, and did; its payload parse then failed, because the row was never written for it, and the job was failed rather than handed back. Three attempts later it was terminal. Refinement is the front door of the product (§10): the visible symptom was a request that stalled in *Refining* forever, with nothing on screen and nothing in the requester's power to explain it, on an instance whose only sin was having a runner switched on. Claims are now filtered by a second test that runs in the opposite direction — the row must *name* the execution plane's routing marker, which is a positive requirement silence cannot satisfy — so a daemon sees only work addressed to a runner, however much it advertises. The control plane's own claim is unchanged and still takes everything it did before; it now also drops the marker from the capability union it claims with, so no backend can advertise its way into dispatching a session a second time. No schema change: the marker is already on the row.
- **Cancelling a session with no recorded runner handle could cancel the wrong row and report success.** The fallback matched on the session id in the job payload, and the control plane's own build payload carries the same field — so where a session had both an agent row and a pending control-plane row, which is ordinary rather than exotic, the cancel could take the control-plane row out of the queue, answer *stopped*, and let the session settle as cancelled while the agent holding the real claim was never told and went on to push a branch. §11 says the cancel button must reach the runner; a cancel that reports success without reaching it is worse than one that fails. The lookup is now restricted to rows that require the execution plane's routing marker, and ordered, so two candidates resolve the same way on every replica.
- **A connected agent could write into the transcript of a session it was never given.** The streamed-event frame names its own job id, and nothing checked that the job was one this agent held — or that the handshake had happened at all. A transcript is what a requester and an engineer both read as the account of what happened (§11, §16), so only the worker actually holding the claim writes it; an event for anything else is dropped.
- **An agent reporting a job it no longer held duplicated it.** A `job.result` frame carrying `abandoned` was acted on by job id alone. Returning work to the queue means enqueueing an equivalent row and completing the claim, and the completion is guarded by `claimed_by` while the enqueue was not — so a daemon reporting on a lease that had already lapsed under it left a second copy of a session another worker was at that moment running, with nothing to cancel it. The claim is re-read and checked before anything is written.
- **Every request body carrying an enum failed to bind.** `CharterApiJson` is passed explicitly to `Results.Json` on the way out and is invisible on the way *in*: minimal APIs read a body through the host's `JsonOptions`, which nothing configured. So `PATCH /api/me/preferences` (theme, pane, teaching level), `POST /api/invitations` (roles), `POST /api/repos/{id}/access` with a role grant, and every other body with one of the wire enums in it answered a bare `400` with no body at all — the settings page could not save a preference and a role grant was impossible through the API. The whole suite passed throughout, because a test composes the body object itself and never crosses the wire. `AddCharterApi` now configures the host's options with the same vocabulary the responses are written in, and the omission rule of §7.4 with it, so an endpoint that forgets to name `CharterApiJson.Options` still writes an absent key rather than a null one.
- **`POST /api/repos` answers with the wizard, and the web app now reads it that way.** The client typed the response as a repository and navigated to `repo.id`, which is `undefined` in the body the endpoint actually sends — so connecting a repository through the real API landed on `/settings/repositories/undefined`.
- **`CHARTER_DEFAULT_SESSION_BUDGET_USD` and `CHARTER_DEFAULT_MONTHLY_BUDGET_USD` reach a budget.** Exactly the `CHARTER_MODEL_REFINE` defect, in the budget subsystem: `AddCharterBudgets` registered its own `BudgetOptions` through `TryAdd` with a hardcoded 5 and 500, no host projected `BudgetConfig` into it, and an operator who set a cap silently got a different one. The host now projects both before any subsystem registers a default, and setting an instance up in organisation mode seeds §34.9's org-level `require_approval` budget from them — so the figures reach a row an admin can see rather than an options record nobody consults. `BudgetOptions`' own default for the monthly amount was 500 against a documented 100; it is now 100, and a test asserts the record's defaults and §4.2's cannot drift apart again. Personal mode still seeds no budget at all, which `docs/configuration.md` now states.
- **`CHARTER_LOG_INCLUDE_TRANSCRIPTS` does something.** §19 makes this the switch that lets repository content into the operator's log platform. It parsed, validated, reached `StartupOptions` and stopped — so the safe default held only because Charter logged no transcript body anywhere, which also meant an operator who turned it on to debug a session got nothing for it. Every control-plane model call — refinement, teaching, recap — is now logged through one component: metadata always (model, outcome, latency, token counts, cost, correlation id), bodies only when the flag is set, and a §19 leak warning in the startup log when it is. The decision is made once rather than per sink, because §19 says the warning applies to every sink equally. The agent's own transcript from a runner is still not written to any sink either way; `docs/configuration.md` and `docs/privacy.md` say so rather than implying the flag covers it.
- **`CHARTER_ALLOW_SHARED_POOL` is consulted.** §20b.7 makes pooling a terms-of-service decision the operator takes deliberately, and `CredentialResolver` decided pool membership purely from the grant — so the instance switch did nothing in either position. The shared-pool tier is now skipped outright unless the instance opted in, which means turning the switch off stops honouring grants that are already pooled rather than merely declining new opt-ins. That is the behaviour that matters, because the reason to turn it off is usually that someone has just read their provider's terms.
- **Repository creation is gated by all three of §26.10's gates.** Only the role existed, and not even that: `MemberCapability.CanCreateRepo` was granted to the first admin and then never checked, `CHARTER_ALLOW_REPO_CREATION` was read by nothing, and the provider's own scope was never consulted. The three are now evaluated together and the refusal names whichever gate stopped it. Nothing in Charter creates a repository yet — the §26.4 new-project flow is not built — and `docs/standards.md` and `docs/security.md` say that plainly rather than letting a working gate imply a working feature.
- **Preflight names the database role it connected as, and how the GitHub App key arrived.** Both were parsed and shown nowhere. "Connected as which role" is the whole answer to a migration that cannot create tables, a failure that looks nothing like the connectivity failure the check otherwise reports; and a private key that was base64-encoded twice presents as every GitHub call failing to sign, so the first-run report now says which encoding was accepted and the parser's refusal names double-encoding as the usual cause.
- **`CHARTER_MODEL_REFINE` and `CHARTER_MODEL_TEACH` reach the model client.** Both parsed, validated, and were then ignored: refinement, teaching and the engineer recap each registered their own options record with a hardcoded `claude-sonnet-4-6` on Anthropic, behind a `TryAdd` and a comment saying a host could project `CharterConfig` into it — which no host did. On the documented default install, which is OpenRouter-only, every refinement therefore presented an OpenRouter key to `api.anthropic.com`, took a `401`, and had the credential marked `invalid` for a fault that was entirely Charter's. The recap follows `CHARTER_MODEL_TEACH`, since §4.2 gives it no variable and it is the same kind of call. `CHARTER_MODEL_BUILD` is unchanged and stays a bare Anthropic name: it is handed to an agent CLI rather than called by Charter, and §20b's two surfaces are the point (§4.2, §20b).
- **Preflight checks run.** The §30.1 first-run checks were registered, built and unit-tested, and nothing in the running application ever asked them anything — `Program.cs` went parse, build, migrate, configure, run. They now run at startup, before Kestrel binds a socket, and print the whole list at once rather than the first failure. An unreachable database, an unmigrated schema, a weak or duplicated key, and a missing model credential stop the boot with every blocking failure named and a non-zero exit; a base URL that does not resolve warns and continues, because that name is resolved by GitHub and by browsers rather than by this container, and split-horizon DNS would otherwise refuse to boot a healthy instance.
- **The migrations preflight check looked at the wrong table.** It asked for `__EFMigrationsHistory` while Charter renames the history table to `__charter_migrations_history`, so it would have reported every fully migrated instance as never migrated. Nothing caught it because nothing ran the check.
- Rebuilding an expired preview now clears the artifact row instead of leaving it expired. The card said it was leaving the `expired` state and the stream event said `pending`, but the row still carried the dead host and the old expiry — so the next page load put the dead link straight back under a Rebuild button the requester had already pressed.
- The generic deployment webhook, `POST /api/deployments/{prSha}`, publishes the verification artifact in the same call rather than recording the deployment and waiting for the lifecycle sweep. A preview that was already live could sit on §27.7's skeleton for up to fifteen seconds.
- A model and adapter pairing that cannot authenticate is refused when it is assembled rather than at dispatch, and the refusal names an adapter that can run the model instead — `openrouter/…` models are offered for `pi` and refused for `claude-code`. A self-hosted OpenAI-compatible endpoint now resolves under either spelling of its provider (`openai-compatible/` or `custom/`) instead of being refused by half of Charter.
- An unreachable OpenRouter catalog no longer costs a connection attempt on every price lookup: a failed fetch backs off for five minutes while pricing degrades to the shipped table, and a stale cache is preferred to no cache.
- **Approving a spec is one transaction.** It saved the request's new status and then enqueued the build job separately, so a container that died in the gap left an approved spec, a thread saying *building this now*, and nothing anywhere that would dispatch it. `JobQueue` shares the caller's `DbContext`, so the job is staged in the same change tracker and one `SaveChangesAsync` commits both or neither. The orchestrator's recovery sweep is unchanged and still runs — belt and braces is right for §2.3 — but it is now the second line of defence rather than the only one.
- The *Works* verdict names the session it is asking for a recap of. The session id was in hand at the call site and was being left out of the payload, so `RecapJobHandler` resolved it back from the request and the specification on every recap. *Not quite* still names the specification and not the session, because §11 makes it a new session rather than a resumption of the one the requester rejected.

- **`.github/workflows/agent-session.yml` describes what it does.** Its comments claimed the session branch was pushed with the installation token while the workflow had no commit or push step at all. The shim now does that work, the workflow passes it the branch and the requester, and the comment explaining why `permissions: contents: read` is enough says the true reason: `persist-credentials` puts the installation token in the checkout's git config, and `GITHUB_TOKEN` is never used for a repository write.

- **Spec §10b amended.** The requester view of a Spec now renders `open_questions` alongside title, outcome and acceptance criteria. The spec previously listed open questions on the structured Spec and then said the requester view rendered "nothing else"; both could not hold. Open questions are the one field written *to* the requester, they are what blocks the confirm button, and hiding them left a person with a disabled button and no explanation. `technical_approach`, `scope` and `risks` remain engineer-only and are still absent from the requester payload entirely.

## Versioning

Charter follows Semantic Versioning, with the standard pre-1.0 caveat: **while the version is `0.x`, a minor bump may break things.** Breaking changes are called out under a `Changed` or `Removed` heading and in the release notes.

Two schemas version independently of the application, because a six-month-old instance must still upgrade cleanly:

- The database schema, versioned by EF Core migrations.
- The `.charter/` folder schema, versioned by the `version:` key in each YAML file.

Upgrades that include database migrations are flagged in the release notes so you know to take a backup first. See [`docs/upgrading.md`](docs/upgrading.md).

## Release tags

The in-app update checker reads the GitHub Releases API and compares `tag_name` against the version compiled into the running build, so tags are not free-form:

- **Stable releases** are tagged `vMAJOR.MINOR.PATCH` — for example `v0.4.0`. The leading `v` is required.
- **Prereleases** are tagged `vMAJOR.MINOR.PATCH-<prerelease>` — for example `v0.5.0-rc.1` — and are marked as prereleases on GitHub. Instances running `CHARTER_UPDATE_CHANNEL=prerelease` are offered these; instances on the default `stable` channel are not.
- **Security releases** carry a `[SECURITY]` prefix in the release title. Charter renders those as a persistent, non-dismissible notice to admins and engineers rather than a dismissible banner.
- **Releases including database migrations** carry `[MIGRATIONS]` in the release title or anywhere in the release body. Charter flags those in the notice, so an operator knows a backup is warranted before pulling. The marker is explicit rather than inferred from the prose — a heuristic over release notes would be wrong in exactly the direction that costs somebody a database.

Any tag that does not parse as a version is ignored by the update checker, which means a mistyped tag fails silently rather than loudly. Check the tag before you push it.
