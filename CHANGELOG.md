# Changelog

All notable changes to Charter are recorded here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

Charter has no released versions yet. Development is in **Phase 1 — refinement only, no agent execution**: request intake, the refinement conversation, the spec confirmation card, and the approval queue. Agent execution, pull request creation, preview binding, teaching, and budgets arrive in later phases. The full build order is section 23 of [`agent-docs/spec.md`](agent-docs/spec.md).

Expect breaking changes without deprecation cycles until 1.0.

### Added

- Repository groundwork: license, contributor license agreement, trademark policy, security policy, contribution guide, and code of conduct.
- Identity behind a single provider seam: email and password (always available), plus GitHub, Google, Discord, and Slack OAuth when configured. Password verifiers use ASP.NET Core's `PasswordHasher`; the plaintext is never stored or logged. A federated sign-in links to an existing account and never creates one.
- Authorization: repository scope with deny by default, additive roles, transcript and code visibility gated on repository read access, and auto-dispatch policy resolution where a repository may only tighten organisation policy.
- First-run setup mode: an instance with zero users serves only the setup route and prints a one-time setup token to stdout. The token creates exactly one admin account, then setup ends permanently.
- Audit log write path, with authorization grants carrying the verb they should be recorded under.
- Refinement conversations are persisted, so a conversation survives the container restarting under it. Requester turns keep their type through storage: a reloaded turn refuses to be read as model-authored text.
- Model credentials: a `cursor_api_key` kind for the `cursor-agent` adapter, a separately tracked overflow allowance so the resolution chain's second tier can fire, a recorded reason when a credential is marked invalid, and a `429` with no reset header now records no reset time rather than a far-future placeholder.
- A refinement conversation read back out of Postgres becomes the live aggregate again, rules and all: the promotion gate, the unread-flag gate, and the confirmation. A confirmation is honoured only while the stored fingerprint still matches the stored spec, so a spec edited behind one comes back unconfirmed rather than dispatchable.
- The refinement thread is rebuilt from the stored turns. A clarifying question, an answer to it, or a turn submitted through `POST /api/requests/{id}/refinement` now survives a refetch instead of existing only in the live broadcast.
- User preferences are columns: theme, pane, and the requester onboarding timestamp join teaching level, so `PATCH /api/me/preferences` writes something instead of accepting the change and dropping it. An unchosen pane is stored as unchosen, which is what lets §12's role default — requesters to pane 1, engineers to pane 3 — apply until somebody picks.
- Requester feedback is recorded. `POST /api/requests/{id}/feedback` writes a row per verdict rather than only enqueueing a job, and the status thread renders the latest one back. Two buttons, *Works* and *Not quite*, as §11 specifies — there is no third.
- `pull_requests` records the head branch, so the engineer `Details` disclosure on the verification artifact card names it instead of showing a blank.
- **`IVersionControlProvider`** (change spec 001 part A.2): every version-control operation — authenticating a repository to a scoped short-TTL credential, describing a checkout, creating a branch, publishing a ref, opening a change request, commenting on one, labelling one, reading its state, comparing revisions, registering a webhook, and the optional create, transfer and protect operations — now sits behind one seam, with a capability model that says what a provider can actually do. GitHub is the only implementation, and it wraps the existing client rather than replacing it. There is still no way to express a merge, at either layer.
- **Change requests are opened from completed sessions.** When a session's runner reports a clean completion, the reconciliation pass publishes the session branch and opens a change request against the repository's base branch, recording its number, URL, head revision, branch and state. It is driven from reconciliation rather than from the result callback, so a control plane that restarted between the two still opens it, and a second pass is a no-op rather than a second change request. A session that produced no changes is recorded as exactly that — a real outcome with its own event and its own sentence, not an error.
- **Change request labels** follow the spec that asks for them: `unreviewed-spec` when the session was auto-dispatched (§7.5) and `schema-change` when the session's migration classification says so (§15). Where a provider has no labels, both facts are stated in the change request body instead of being dropped.
- **Change request state tracking** from the existing GitHub webhook, and §17 staleness: an open change request is marked stale when it is behind the base branch **and** overlaps it on changed files. Being merely behind is not stale — most open change requests are behind most of the time, and a flag that fires on all of them is one everybody ignores.
- **Onboarding verifies the merge gate** (change spec 001 part A.5). A repository whose base branch has no protection rule requiring review is reported as `advisory` rather than `provider_enforced`, warned about in the onboarding wizard, and recorded in the audit log whichever way the check comes out. Protection Charter cannot read is reported as "not verified", never as protected. `docs/security.md` gains a section stating this plainly.
- **A session that changed nothing has its own outcome.** §6 gains `NoChangesNeeded`, terminal and separate from `Failed`, because the agent running correctly and finding nothing to do is not a failure. The requester reads *"Nothing needed changing"*, with the sentence that matters underneath it: *"Nothing needed changing here. Most often that means what you asked for already works the way you wanted. Nothing went wrong, and there is nothing for you to do."* It notifies nobody and pages no engineer. Previously such a session ended as `Failed`, whose copy — *this turned out to be bigger than expected* — was the opposite of what had happened.
- **Preview environments can be reported by change request comment.** §18's fallback path is now connected end to end: the GitHub webhook delivery carries the comment's issue number, author and body, and an `issue_comment` listener hands them to the deployment ingestor. The parser and the binding already existed; nothing could reach them. The body is truncated on the way in and read only for a URL and a state, and a comment on a change request Charter did not open is ignored.
- **Change requests record their author.** `change_requests.author_login` is populated when the change request is opened, so §18's warning about Railway refusing to deploy a branch from an account outside the workspace can name the account to invite instead of saying "the author". A preview that never arrives with no explanation is the worst version of that failure.
- **Email delivery** (change spec 001 part C), behind an `IEmailProvider` seam with one implementation: SMTP. One implementation reaches SES, Postmark, Mailgun, Resend's SMTP endpoint, Google Workspace and a self-hosted relay, and needs no vendor account to test against. It is a hand-written client over `TcpClient`/`SslStream` rather than `System.Net.Mail.SmtpClient`, which cannot do implicit TLS. `CHARTER_EMAIL_PROVIDER=resend` is recognised and rejected with a message saying what to do instead, rather than treated as an unknown value.
- **`none` is a supported email configuration, not a broken one.** With no mail server, an administrator creating an account is shown the one-time setup link to pass on themselves; a failed send falls back to the same link, because the alternative is an account nobody can sign in to. Password reset by email is disabled with an explanation, and the link is never shown to whoever typed an address into the forgot-password form — anybody can type anybody's address into it. Every email-dependent setting reports why it is off and names the variables to set.
- **A test email can be sent from settings.** Through the real send path, not around it. Email misconfiguration is otherwise discovered when an invitation silently fails and a new hire cannot log in.
- **Notifications** (§22): one outbound abstraction, a per-user channel preference, and email as the only channel with an implementation. The notify-worthy set is a closed, tested list of exactly two states — `NeedsInput` and `PreviewReady` — checked once in the dispatcher rather than at each call site. §6 is explicit that notifying on all of them gets Charter muted within a week, and every other state is individually persuasive to whoever is adding it.
- **Templates in HTML and plain text** for invitation, password reset, *question for you*, *ready to try*, and the settings test. Both renderings are built from one structure, so they cannot drift. The copy follows §11 — plain language, no ETA, no jargon — and the requester-facing models have no field for a repository, branch, commit or cost, with a scrubber removing commit hashes, forge URLs and stack frames from the free text they do carry. A requester's own words are left alone.
- **Delivery failures are logged, recorded and returned** rather than swallowed, including a provider that throws: a notification is a side effect of a state transition, and a transition must not roll back because a mail server was down. The recent-delivery list is what the admin settings page reads; it is a table, retained for 30 days or 2,000 attempts.
- **The stores that were in memory are in Postgres** (§2.3): the per-user concept ledger, the walkthrough cache, the *explain this* daily cap, the per-user notification channel preference, and the email delivery log. Each replaces a working in-process default that lost everything on restart — a requester re-taught what a migration is because the container moved, a walkthrough re-billed to the teaching budget line for text that had already been written, and a delivery list that went blank on exactly the redeploy an operator reached for when mail looked broken. Four tables join `InitialCreate`: `notification_channels`, `email_deliveries`, `invitations` and `explain_this_usage`, and `concept_ledger` gains `last_referenced_at` (amending spec §5). No backfill: a user with no `notification_channels` row keeps the default of email on, Slack and Discord off.
- **Invitations are a row** (§30.2): email, roles, inviter, expiry, single-use redemption, and a SHA-256 digest of the emailed token. The token itself is never stored, so a database dump cannot be replayed against the redemption endpoint and a lost invitation is reissued rather than recovered. Redemption is one conditional `UPDATE`, so two clicks on the same link at the same instant produce one account and one refusal.
- **The email delivery log is retained rather than unbounded**: 30 days or 2,000 attempts, whichever comes first, pruned by Charter and not by an operator remembering to. A permanent record of every address this instance has ever written to is its own problem.
- **Outbound mail is rate-limited per recipient** in a sliding one-hour window, `CHARTER_EMAIL_MAX_PER_HOUR`, default 20. Account mail and notifications are counted in separate buckets so a burst of status mail cannot starve the invitation somebody is waiting for.
- Verification artifacts carry a jsonb payload for §27.7's kind-specific bodies: checksums and sizes for a build, the capture list for screenshots, counts and assertion text for a test report, device identifier and traces for a hardware-in-the-loop run. Nothing is invented at read time — an unrecorded field stays empty, an unprobed preview reports `unknown`, and a hardware run with no recorded outcome does not claim it passed.

### Changed

- **`PullRequest` is renamed `ChangeRequest`** throughout the data model, the API and the code (change spec 001 part A.2, amending spec §5). The table is `change_requests`, `deployments.pull_request_id` is `change_requests.change_request_id`, and the API's engineer `details` payload renames `pullRequestNumber` and `pullRequestUrl` to `changeRequestNumber` and `changeRequestUrl`, alongside a new `changeRequestTerm` carrying the provider's own word — *pull request* on GitHub, *merge request* on GitLab — so the UI stops hard-coding one provider's vocabulary. This is a breaking API change; there are no released versions, and the initial migration was amended in place rather than a rename migration being added.
- **The control-plane model defaults are OpenRouter-qualified.** `CHARTER_MODEL_REFINE` and `CHARTER_MODEL_TEACH` now default to `openrouter/anthropic/claude-sonnet-5`, reached by `OpenAiCompatibleModelClient`: one implementation, one key, every model. The native Anthropic and Gemini clients stay registered and are used the moment an `anthropic/` or `google/` identifier is configured — this is a default, not a deletion. An instance holding only an `ANTHROPIC_API_KEY` should set those two variables explicitly or add an `OPENROUTER_API_KEY`. `CHARTER_MODEL_BUILD` deliberately does **not** change: it is handed to an agent CLI, not called by Charter, so it stays a bare Anthropic name the default adapter can actually run (spec §4.2, §20b).
- **`adapters/pi.yml` rewritten against pi's published CLI reference.** The shipped file was the illustrative snippet from spec §12b and was wrong in four ways: `--mode json` is the event stream (`--print` is a different mode and `--output-format` does not exist), the message is a positional argument, `--provider` and `--model` are separate options, and the JSONL events are `tool_execution_start` / `message_end`, not `tool_call` / `assistant`. Spec §12b's worked example has been corrected to match. `steering` is no longer claimed for `pi` or for `claude-code`: pi steers through `--mode rpc` and Claude Code through `--input-format stream-json`, neither of which the shim speaks yet.
- **Adapters declare the model identifier form their CLI expects**, through a new `model_format` key — `bare` (the default, and what Charter dispatched before), `qualified`, or `verbatim` — plus a `{provider}` placeholder for a CLI that selects the provider separately. `claude --model anthropic/claude-opus-5` and `opencode run --model claude-opus-5` are both unknown-model errors, and the caller no longer has to know which is which. Existing adapter files keep producing exactly the command they did before.

### Fixed

- Rebuilding an expired preview now clears the artifact row instead of leaving it expired. The card said it was leaving the `expired` state and the stream event said `pending`, but the row still carried the dead host and the old expiry — so the next page load put the dead link straight back under a Rebuild button the requester had already pressed.
- The generic deployment webhook, `POST /api/deployments/{prSha}`, publishes the verification artifact in the same call rather than recording the deployment and waiting for the lifecycle sweep. A preview that was already live could sit on §27.7's skeleton for up to fifteen seconds.
- A model and adapter pairing that cannot authenticate is refused when it is assembled rather than at dispatch, and the refusal names an adapter that can run the model instead — `openrouter/…` models are offered for `pi` and refused for `claude-code`. A self-hosted OpenAI-compatible endpoint now resolves under either spelling of its provider (`openai-compatible/` or `custom/`) instead of being refused by half of Charter.
- An unreachable OpenRouter catalog no longer costs a connection attempt on every price lookup: a failed fetch backs off for five minutes while pricing degrades to the shipped table, and a stale cache is preferred to no cache.

- **Spec §10b amended.** The requester view of a Spec now renders `open_questions` alongside title, outcome and acceptance criteria. The spec previously listed open questions on the structured Spec and then said the requester view rendered "nothing else"; both could not hold. Open questions are the one field written *to* the requester, they are what blocks the confirm button, and hiding them left a person with a disabled button and no explanation. `technical_approach`, `scope` and `risks` remain engineer-only and are still absent from the requester payload entirely.

## Versioning

Charter follows Semantic Versioning, with the standard pre-1.0 caveat: **while the version is `0.x`, a minor bump may break things.** Breaking changes are called out under a `Changed` or `Removed` heading and in the release notes.

Two schemas version independently of the application, because a six-month-old instance must still upgrade cleanly:

- The database schema, versioned by EF Core migrations.
- The `.charter/` folder schema, versioned by the `version:` key in each YAML file.

Upgrades that include database migrations are flagged in the release notes so you know to take a backup first. See [`docs/upgrading.md`](docs/upgrading.md).

## Release tags

The in-app update checker reads the GitHub Releases API and compares `tag_name` against the version compiled into the running build, so tags are not free-form:

- **Stable releases** are tagged `vMAJOR.MINOR.PATCH` — for example `v0.4.0`. The leading `v` is required.
- **Prereleases** are tagged `vMAJOR.MINOR.PATCH-<prerelease>` — for example `v0.5.0-rc.1` — and are marked as prereleases on GitHub. Instances running `CHARTER_UPDATE_CHANNEL=prerelease` are offered these; instances on the default `stable` channel are not.
- **Security releases** carry a `[SECURITY]` prefix in the release title. Charter renders those as a persistent, non-dismissible notice to admins and engineers rather than a dismissible banner.

Any tag that does not parse as a version is ignored by the update checker, which means a mistyped tag fails silently rather than loudly. Check the tag before you push it.
